# Retail Inventory Intelligence

A single-page analytics dashboard for a synthetic retail inventory dataset, built as a
Data Analyst portfolio project: **Python + Pandas** for the analysis, **React + Vite + Recharts**
for the front end. Dark, card-based, responsive, no backend.

## What the data says

| Measure (full period) | Value |
| --- | --- |
| Units sold | **6,750,876** |
| Demand | **7,928,104** |
| Units ordered | **6,770,889** |
| Average inventory | **301.1** units (day-weighted) |
| Fulfilment rate | **85.2%** |

76,000 daily rows · 1 Jan 2022 – 30 Jan 2024 · 5 stores · 20 products · 100 product–store pairs ·
5 categories · 760 trading days.

The dashboard's headline finding is consistent and uncomfortable: **inventory cover is thin
everywhere**. Every one of the 100 product–store pairs sits below 7 days of cover
(1.08–5.25 days, median 2.96), so the status mix is **50 Critical / 50 Low Stock / 0 Healthy /
0 Overstock / 0 No Demand**, and every store carries risk on all 20 of its pairs. Store sales are
near-tied (S002 1,386,126 · S003 1,375,613 · S005 1,362,812 · S001 1,318,134 · S004 1,308,191) and
demand is broadly flat across 25 months, so the dashboard deliberately leads with *where cover is
thinnest* rather than with sales bravado.

## Quick start

```bash
# 1. rebuild the prepared datasets from the cleaned analysis output
python analysis/build_dashboard_data.py

# 2. run the dashboard
npm install
npm run dev        # http://localhost:5174

npm test           # metrics verified against pandas-computed reference values
npm run build      # production bundle
npm run preview    # serve the production bundle
```

Everything the front end reads lives in `data/` and is regenerated by step 1.

## Project layout

```
analysis/build_dashboard_data.py   pandas pipeline: corrected datasets, app payload, test reference
data/                              generated: prepared CSVs, dashboard-data.json, expected_reference.json
src/lib/                           constants, formatting, dataset loader, metrics (all calculations)
src/state/useDashboard.js          filter state + memoised derived views
src/components/                    Sidebar, Header, FilterBar, kpi/, charts/, health/, table/, ui/
tests/metrics.test.js              asserts the JS metrics against the pandas reference
output/                            untouched notebook artefacts (see "Prepared data" below)
data.ipynb, sales_data*.csv        original analysis notebook and source datasets
```

Calculation logic never lives in a component: `src/lib/metrics.js` exposes pure functions
(`summarize`, `computeKpis`, `buildPairAggregates`, `buildStoreRisk`, …) that every card consumes.

## Filters and what they affect

| Control | Affects |
| --- | --- |
| Store, Category, Product | Every KPI, chart, health view and table row |
| Period (presets, or a custom from/to month) | Every KPI, chart, health view and table row |
| Inventory status | Inventory health views and the inventory table only — sales and demand metrics always cover every status |
| Table search | The inventory table only (matches product ID, store ID, category) |

Because days of cover is derived from the selected window, changing the period recalculates cover,
status and suggested reorder quantities for every pair — the table, badges and health cards stay
internally consistent.

## Method and assumptions

* **Average inventory** — day-weighted mean of the daily `Inventory Level` for a pair.
* **Average daily demand** — summed demand ÷ trading days in the selected window.
* **Days of inventory** — average inventory ÷ average daily demand.
* **Inventory status** (project-defined thresholds for this exercise, *not* industry standards):
  `< 3` Critical · `3 – < 7` Low Stock · `7 – 30` Healthy · `> 30` Overstock Candidate ·
  zero demand → No Demand.
* **Replenishment illustration** — 5 day lead time + 2 days of safety stock; reorder point =
  average daily demand × 7; suggested reorder qty = `max(reorder point − average inventory, 0)`.
  Illustrative only, not a purchasing recommendation.
* **Fulfilment rate** — total units sold ÷ total demand (never an average of row-level ratios).
* **Monthly Demand** — defaults to the real 25-month time series; the toggle switches to the
  calendar-month seasonality view, which aggregates across years.

### Prepared data

`output/dashboard_inventory.csv` (written by the original notebook) computes `Avg Inventory` as
`mean(Inventory Level) / day count`, which understates inventory by the day count
(0.13–0.78 instead of 100–590) and inflates `Suggested Reorder Qty` to 502–873 instead of
132–721. `Avg Daily Demand`, `Days of Inventory` and `Inventory Status` in that file are correct.

`analysis/build_dashboard_data.py` writes **corrected copies** to `data/` (plus the category, store,
status and monthly datasets the notebook did not export) and leaves `output/` and `data.ipynb`
untouched. The dashboard reads only `data/`.

## Testing

`npm test` compares the dashboard's own calculations with values computed independently in pandas
(`data/expected_reference.json`, 8 filter scenarios including an empty one): KPI totals, average
inventory, fulfilment rate, pair-level cover/status/reorder quantities, store risk ranking,
threshold boundaries, the empty-selection behaviour and the demand series length. If either
pipeline drifts, the suite fails.

```bash
python analysis/build_dashboard_data.py   # regenerates the reference values
npm test
```

## Data provenance

Synthetic retail inventory dataset, analysed with Python + Pandas. It does **not** represent any
real retailer and carries no affiliation with Walmart, Amazon or anyone else. Figures shown in the
dashboard are calculated from the CSVs in this repository — nothing is hard-coded.

## Known limitations

* The data is bundled with the front end at build time (no async fetch), so no loading skeletons are
  needed; empty filter combinations render explicit empty states instead of blank cards.
* Recharts dominates the production bundle (~214 kB gzipped). Acceptable for a portfolio demo;
  hand-rolled SVG charts would cut it substantially.
* The dataset's synthetic generator produced uniformly thin inventory cover, so the health views
  exercise their zero states heavily — that is the data, not a display bug.
